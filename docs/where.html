Check your own machine instead of trusting a table

aem scan resolves every path through the same registry, reports installed / config-only / absent per tool, and counts the skills it can see. It is read-only: no library is created, nothing is written.

# after: pip install git+https://github.com/Jack91124/ai-extension-manager
aem scan

# resolved skills / MCP / rules paths for each tool, with scope
aem dirs --existing

# machine-readable, for scripts and dashboards
aem scan --json

# one tool only; exit 1 if it is not installed
aem scan --agent claude --require claude

Copy a skill from one tool to the others

Copy is the default because symlinks break on Windows junctions, sandboxes and tools that hash the directory. aem hashes the library, the last synced copy and the current target before it writes.

# 1. pull one skill into the central library (never overwrites your library copy)
aem import --source ~/.claude/skills/my-skill

# 2. distribute it to any compatible tools
aem sync --direction distribute --agent codex --agent cursor --resource my-skill

# 3. prove the copies still match the library
aem verify --all

# 4. if both sides changed, aem stops with exit code 2 and writes nothing
aem compare --resource my-skill --agent codex
aem sync --direction distribute --agent codex --resource my-skill --on-conflict keep-target

Why not just symlink the directory?

You can — --mode link exists for that, and aem verifies the target resolves before it reports success. But links are the wrong default here:

Windows

Directory symlinks need Developer Mode or elevation; junctions are per-directory and confuse tools that walk the tree. A copy always works.

Divergence is the point

You edit the copy a tool actually loads. A link hides that edit; a copy plus a hash record lets aem tell you exactly which side moved.

Sandboxes and packaging

Some tools hash, snapshot or ship their skill directories. A link silently changes the payload; a copy keeps every tool self-contained.
